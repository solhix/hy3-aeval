## 做得好的部分（应保留）

1. **判题平台工程扎实**：FastMCP 服务、服务端强制判题参数/提交次数/MD5 去重、隐藏数据不回传 `expected_output`、WSL cgroup v2 兼容处理、Judge0 故障重试不扣次数——这些都不是凑数，是真正可用、可复现的评测基础设施。
2. **题集质量高**：8 道真题来源清晰（洛谷题面 + 博客标准答案），`problems.json` 含知识点、时限/内存、官方值与本地放宽值对照，分层依据写明了。
3. **仓库规范**：README 把架构、目录、配置、环境变量、快速开始、新增题目流程都讲清楚，含 judge0 部署包与 GPL-3.0 合规说明，符合"开源项目仓库 + README + 环境配置样例"要求。
4. **答案准确率结果可信**：One-Shot 约束、运行态校准（不只信 verdict 字段）、分层通过率，口径严谨。

## 核心缺陷（必须补才能算完成任务二）

- **整条"过程评估"主线缺席。** 任务二的名字就是"过程评估与错误定位"，四个必需能力（过程正确性判定 / 错误步骤定位 / 错误类型归类 / 正确但过程不成立识别）一个都没落地。报告里的"错误类型分布"是 judge0 的 AC/WA/TLE/CE 运行态，与任务的"错误分类体系"（题意误读、概念理解错误、计算错误、条件遗漏、跳步推导、格式不符…）是两回事——**统计口径对错了对象**。
- **没有"过程正确率"指标**，也没有定位准确率 / 误报率的有效性验证。这两项是任务二"有效性验证"的硬性两条，目前完全空白。
- **应用侧偏"答题器"而非"解题过程评估器"**：被测模型确实在对话里会推理，但系统不捕获、不结构化、不评估这段推理，等于默认"最终 AC 即正确"，正好踩中任务禁止的"仅判断测试是否通过"。

## 建议的补齐路径（若要拿到任务二高分）

1. 新增**过程评估模块**（独立于 judge0 判题）：让被测模型在提交代码前/后输出结构化解题过程（思路、复杂度分析、边界处理、关键步骤），由分步 LLM 审查 + 规则校验（如复杂度是否与时限匹配、边界样例是否覆盖）给出过程判定。
2. 建立**推理错误分类体系**（题意误读/概念错误/计算错误/条件遗漏/跳步/格式不符…），并与 judge0 运行态区分开统计。
3. 实现**错误步骤定位**（过程链条中首个不成立步骤）与**"答案对但过程不对"识别**（如空跑巧合、靠样例硬编、数值巧合）。
4. 跑**有效性验证**：在已知错误样本上测定位准确率，在已知正确样本上测算误报率，附人工抽检记录。
5. 报告补**过程正确率、错误类型分布（过程维度）、难度分层的过程表现、能力边界分析**。
