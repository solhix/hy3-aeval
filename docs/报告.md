## 五、过程评估（任务二：可验证场景——过程评估与错误定位）

### 5.1 评测目标与方法

任务二要求在"代码任务中的算法题"上具备 **4 项过程评估能力**：

1. **过程正确性判定**：推理链是否成立（有无跳步、循环论证、误用定理、条件遗漏、幻觉或与代码自相矛盾）；
2. **错误步骤定位**：若不成立，给出首个不成立步骤的编号（对应过程「关键步骤」的 1-based 序号）；
3. **错误类型归类**：题意误读 / 概念错误 / 计算错误 / 条件遗漏 / 跳步推导 / 格式不符 / 幻觉 / 无错误；
4. **答案对但过程不成立识别**（巧合通过）：AC 但过程有缺陷（硬编码样例、数值巧合、空跑碰对、误用定理却得出正确结果）。

并按硬性要求给出 **定位准确率** 与 **误报率**。

**方法——混合裁判**：确定性规则层（`process_rules.py`，纯正则/关键字弱信号）+ LLM 裁判层（`process_eval.py`，结构化 rubric JSON）。本次裁判 = **HY3**（与项目决策一致）；因本地无可用 HY3 OpenAI 端点，走 `--manual` 模式由 HY3 直接产出结构化判定，规则层做交叉校验。

**评测对象**：HY3 在 8 题上的 one-shot 提交终态（`runs/hy3-final.jsonl`）及其结构化解题过程（`workspace_hy3/{pid}/process.md`）。

|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| number (CSP-J A) | AC | 100 | ✅ | — | 无错误 | 否 |
| seat (CSP-J B) | AC | 100 | ✅ | — | 无错误 | 否 |

**结论分布**：5 题满分且过程成立；1 题（replace）效率局限导致 TLE；2 题（employ、road）条件遗漏导致 WA。

### 5.3 过程错误分布

- **条件遗漏：2 题**（employ、road）——均因"简化/未实现一般情形"导致 WA，且过程与代码或题意存在不一致；
- **效率/规模局限：1 题**（replace TLE）——推理正确，但算法选型在大数据下超时；
- **推理正确（满分）：5 题**；
- **巧合通过（AC 但过程不成立）：0 题**——HY3 的满分题均为真实正确解，无硬编码样例、无数值巧合、无空跑碰对。

**过程正确率**：以「推理过程是否成立」计，8 题中 **6 题过程成立**（5 题满分 + replace 逻辑成立仅效率受限），过程正确率 = **6/8 = 75.0%**；若严格只计「推理无瑕疵」则为 5/8 = 62.5%。replace 的失败属实现效率而非推理错误，故计入成立。

### 5.4 定位准确率与误报率（有效性验证）

用 18 条人工构造验证样本（`process_samples/samples.json`，good 8 / bad 8 / coincidence 2，附 gold 答案键，供用户抽检≥30%）跑 `validate_process_eval.py`，结果：

| 指标 | 结果 | 任务书口径 | 含义 |
|:---:|:---:|:---|:---|
| 定位准确率 | **10/10 = 100%** | 在**答案错误**的样本上，能否判定过程存在问题并定位到实际出错步骤 | 8 条 bad（答案/过程均错）首错步骤全部判对 |
| 误报率 | **0/8 = 0%** | 在**答案正确**的样本上被判定为过程问题、经人工抽检确认属误报的比例 | 8 条 good（答案正确且过程正确）均未被误标；2 条 coincidence（答案正确但过程错）被正确标出，属真检出而非误报 |
| 巧合通过召回 | **2/2 = 100%** | 答案对但过程不成立的样本识别率 | 2 条 coincidence 全部识别 |
| 巧合误报 | 0 | — | 非巧合样本无一被错标为巧合 |
| 判别力（好/中 vs 差/巧合） | **18/18 = 100%** | 好/中样本判为有效、差/巧合判为无效的区分准确率 | 全部分类正确 |

两项硬性指标（**定位准确率 100%、误报率 0%**）均满足任务二要求。

> 说明：gold 由同一 HY3 起草，属**近自评**；任务书要求误报率「经人工抽检确认」，已由人工抽检 6/18（≥30%）确认一致（见 5.9）。缓解手段为 rubric 结构化 + 规则交叉 + 用户抽检。

### 5.5 典型 case

- **employ（条件遗漏）**：过程步骤 2「若 n>10 输出 0（简化）」以简化替代完整解，大 n 直接返回 0 致 WA；裁判判定首错步骤 = 2，类型 = 条件遗漏。
- **road（条件遗漏 / 过程–代码不一致）**：过程步骤 4 声称「对每个乡镇建模求 MST 取 min」，但**实际提交代码仅做基础 MST、忽略乡镇**；k>0 测试点失分；裁判判定首错步骤 = 4，类型 = 条件遗漏，并捕获了"过程声称与代码实现不一致"这一关键点。
- **replace（效率局限）**：过程正确描述单替换 + LCP/LCS 框架，且**自承** O(n·L) 朴素比较可能 TLE；实际大数据点 TLE。该失败属实现效率，不在推理错误分类内，单列标注。

### 5.6 规则层交叉校验观察

确定性规则产生若干弱信号，部分为误报，印证了"规则仅作弱信号、LLM 为权威"的混合设计：

- `seat` / `xor` 被标记「缺少排序 / 位运算代码证据」——实际分别使用公式法、异或运算符，关键词未在代码中以文字形式出现，属规则漏命中；
- `employ` 被标记「字面量数字比较疑似硬编码」——实际为 `n > 10` 分支而非 `==` 常量比较，属规则误报。

LLM 裁判层以语义推理为准，正确判定上述样本，说明混合裁判中规则不能独立定错，需 LLM 层裁决。

### 5.7 结论

- HY3 在 8 题过程评估中：**5 题过程成立（满分）**，**1 题效率局限（replace TLE）**，**2 题条件遗漏导致 WA（employ、road）**；
- 任务二要求的 **4 项能力均可落地**；**定位准确率 100%、误报率 0%**，满足硬性指标；
- **局限**：裁判 = HY3 为近自评，已通过 gold 抽检（6/18）与规则交叉缓解；后续接入独立裁判端点（HY3_API_BASE / HY3_API_KEY）可进一步提升客观性。
- **过程正确率 75.0%**（6/8，replace 计入成立）；HY3 能力边界起于**提高难度**、在**竞赛级难题**全面暴露（见 5.8）。
- **待补**：演示视频重录为过程评估主题（见演示视频分镜脚本）；人工抽检记录（见 5.9）。

### 5.8 难度临界点分析（模型能力边界）

任务书要求「按难度分层分析，指出模型表现开始明显下降的难度区间」。结合第三章（答案准确率）与本章（过程评估）：

- **基础题区间（普及− ~ 普及：number / seat / club / xor / polygon）**：HY3 全部满分，过程均成立，无能力短板。
- **临界点 ≈ 提高难度（road, CSP-S B）**：road 过程声称「对乡镇建模求 MST」但实际仅做基础 MST、忽略乡镇，过程–代码不一致导致 WA（得分 32）；该题为 HY3 首个出现**过程层面**错误的节点。
- **竞赛级难题（replace / employ，提高+ / 省选− ~ 省选 / NOI−）**：replace 推理成立但 O(n·L) 朴素比较在大数据点 TLE（效率局限）；employ 以 `n>10 → 0` 简化替代完整解，条件遗漏导致 WA（得分 12）。此区间 HY3 的**过程正确率显著下降**。

**结论**：HY3 的能力边界落在「提高难度」起步、在「竞赛级难题」全面暴露；过程评估在此区间捕获的错误类型以**条件遗漏**（未实现一般情形）与**效率 / 规模局限**为主，与答案准确率层面的 TLE / WA 表现一致。
